# MI2 difficulty bit and Room108 reclassification (17 November 2026)

**Evidence boundary:** Independent read-only search of fingerprinted original DOS VGA `MONKEY2.001` (SHA-256 `ad045372e0d49626503bb50fca29a687ec8e01ef75d9b8bca702a366d143819e`), with `DSCR` resource IDs taken from its paired `MONKEY2.000`. Script opcode interpretation cross-referenced to [ScummVM v2026.4.0 v5 handlers](https://github.com/scummvm/scummvm/blob/v2026.4.0/engines/scumm/script_v5.cpp) (`o5_move`, `o5_notEqualZero`, `o5_print`, `o5_stringOps`). **No live run, independent descumm pass, rendered-frame verification, or new decoder feature.** No copyrighted game art/text resource is committed.

## Finding A: Bit567 is the Regular/Easy mode selection flag

The exact v5 direct-assignment bytecode sequence `1A 37 82 NN 00` writes `Bit[567]=NN`. Three separate original global-script resources contain *pairs* of these assignments immediately associated with corresponding original mode labels:

| Global script (archive storage room) | Original decoded absolute opcode offset | Assignment | Nearby in-game label |
| --- | ---: | --- | --- |
| DSCR 1 (room4) | `0x355F7` | `Bit[567]=0` | “Regular Mode” |
| DSCR 1 (room4) | `0x36F0B` | `Bit[567]=1` | “Easy Mode” |
| DSCR 4 (room4) | `0x37677` | `Bit[567]=0` | “Regular Mode” |
| DSCR 4 (room4) | `0x3768F` | `Bit[567]=1` | “Easy Mode” |
| DSCR 131 (room108) | `0x8727E7` | `Bit[567]=0` | “Regular Mode” |
| DSCR 131 (room108) | `0x87281E` | `Bit[567]=1` | “Easy Mode” |

The pairs plus textual labels are **strong, independent source evidence** for the semantic interpretation of Bit567. It is NOT an arbitrary unknown story flag. `0x8000 | 567 = 0x8237` explains why the little-endian operand is `37 82`.

**Important nuance:** the table certifies original script storage and directly encoded assignments; it does not prove which mode menu or source-script branch ran in a particular recorded game session. We have not independently descumm-aligned all of global scripts 1/4/131. Do not reinterpret a stored “Easy Mode” assignment as runtime confirmation without logging the branch.

### Archive-wide implications

A read-only scan over `ENCD`, `EXCD`, `LSCR`, indexed global `SCRP`, and `OBCD/VERB` script areas found **114 occurrences** of the 2-byte variable address `37 82` in **82 resource bodies stored across 34 room bundles**. These are **unaligned address byte-pattern occurrences**, potentially including false positives or incidental data. They do **not** represent 114 confirmed operations nor 34 runtime rooms using difficulty. Nonetheless the widespread presence provides a concrete search worklist.

The known fully aligned **Room35 ENCD** (source offset `0x2B2516`, 160-byte body) has first conditional `notEqualZero(Bit567)`; the true branch executes `move Bit92=1` before testing Bit92 and selecting object states/Room35 waterfall script202. Therefore in the Easy-mode code path Room35 entry **forces the alternate scenery configuration**, whereas Regular mode inherits the preexisting Bit92 state. **This is not proof that Easy mode displays zero palette motion in Room35**; the archive CYCL entries still exist and need separate active-cycle testing.

Other already important original resource bundles referencing Bit567 include **Room7** (our existing panorama benchmark), Room9, Room22, Room35, Room44, Room48, Room72, Room79, etc. Tests must **record game mode** in manifests. It is unsafe to claim a single captured frame sequence is representative of both modes.

## Finding B: Room108 is startup/copy-protection/difficulty UI content, not an ordinary outdoor animation scene

Room108 contains four paired image objects: IDs 1154/1155 each **15 image states**, IDs1156/1157 each **2 image states**, total **34**. The previously published `MI2_GLOBAL_SCRIPT_PATTERN_SURVEY_20261116.md` identified 18 unaligned global-script direct-object candidates and treated Room108 as an unknown animation target.

The original indexed global scripts stored in Room108 are **DSCR 128–136 and 142**. Text content from original `SCRP[128]` directly identifies the screen with **copy protection** and a **“MONKEY 2 LITE”** choice. `SCRP[131]` includes the two directly coded Bit567 Regular/Easy assignments tabulated above. `SCRP[134]` contains responses to incorrect input combinations, and `SCRP[135]` contains a lengthy ingredient-list table. These are original data-backed clues to a game startup/protection interaction; they are not a standard scenery animation target.

**Research correction:** Reclassify Room108 as **startup/copy-protection/difficulty-selection UI**, with potentially scripted multi-state graphic components. Do **not** use it to prioritize P4 environmental animation merely because it has 34 stored OBIM states or candidate object-draw instructions. It remains useful for P1 script indexing, P2 multi-image object decode, P6 interface preview and possible independent object state sequencing. The exact role of each image state and authored draw order remains to be verified with aligned disassembly and runtime capture.

## Finding C: global startup scripts initialize shared environment bits

Global script DSCR1 (stored room4) contains pairs of *direct* `move Bit93=1`, `move Bit92=1` near decoded addresses `0x35F45`/`0x35F4A` and `0x36319`/`0x3631E`—two distinct sections of startup logic. These are *source candidates for initial environment state*, NOT a traced normal-start execution path. Their direct opcode shape is clear; caller/branch alignment and the game state after startup have not been independently verified.

Cross-reference [Rooms 35–37 notes](MI2_ROOMS35_36_37_CROSSROOM_CYCL_STATE_20261117.md) and future [Room26 map-routing notes](MI2_ROOM26_WATERFALL_MAP_BOX_STATE_20261117.md). The initial-state connection makes it especially important not to assume Bit92 starts at zero on a new Regular-mode save.
